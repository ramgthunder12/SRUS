### Q1. 28개 요구사항 중 가장 충돌이 컸던 요구사항은 무엇이었나요?

**A.**  
가장 충돌이 컸던 요구사항은 **"NFC 카드 인증 시 어느 시스템이 DB에 접근해야 하는가"** 였습니다.

초기 논의에서는 무인대여함 시스템(RBS)이 직접 DB를 조회해서 인증 여부를 판단하자는 의견이 있었습니다.  
하지만 RBS는 라즈베리파이 기반 임베디드 장치이고, DB 접근 권한을 분산시키면 보안·유지보수 모두 어렵다는 점에서 충돌이 생겼습니다.

최종적으로는 **RBS는 DB에 직접 접근하지 않고, SRUS 메인 서버에 REST API(`/authentication/comparecarduid`)를 호출하는 방식**으로 합의했습니다. 인증데스크(ADS)도 동일하게 `/authentication/grantauthinfo` API를 통해 SRUS 서버가 DB를 단독으로 관리합니다.

이 구조는 실제 코드에서 `AuthenticationController` → `AuthenticationServiceImpl` → `RentalBoxMapper` 계층으로 구현되어 있습니다.

### Q2. 용어 사전 227개를 정의했다고 했는데, 실제로 어떤 용어에서 오해가 있었나요?

**A.**  
가장 혼선이 컸던 용어는 **`rental`(대여)과 `usageHistory`(이용 내역)의 구분**이었습니다.

처음에는 팀원 일부가 두 개념을 동일하게 봤습니다.  
하지만 설계 과정에서 다음처럼 명확히 분리했습니다:

| 용어 | 의미 | 발생 시점 |
|---|---|---|
| `rental` | 결제·예약 레코드 (언제부터 언제까지, 얼마 결제) | 사용자가 웹에서 결제할 때 |
| `usageHistory` | 무인대여함 실제 개방·반납 기록 | RBS 장치에서 NFC 인증 성공 시 |

두 번째로 오해가 있었던 용어는 **`division`** 이었습니다. 이 컬럼이 세 테이블에 존재하지만 의미가 각각 다릅니다:

- `member.division` → 회원 역할 (`'M'` = 일반 회원, `'A'` = 관리자)
- `rental_box.division` → 대여함 운영 상태 (`'Y'` = 운영 중, `'D'` = 삭제/비운영)
- `usage_history.division` → 출입 구분 (입장/퇴장)

세 번째는 **`AUTH_KEY`와 `CARD_UID`의 관계**입니다. 둘이 별개 값이라고 오해한 팀원이 있었는데, `AUTH_KEY`는 사실 `CARD_UID`를 `rental_box` 테이블에 일시적으로 복사한 값입니다. `grantAuthInfo()` 코드에서 `rentalBox.setAuthKey(row.getCardUid())`로 확인할 수 있습니다.

### Q3. ERD를 설계할 때 가장 많이 고민한 테이블은 무엇이었나요?

**A.**  
**`rental_box` 테이블**이었습니다.

이 테이블은 성격이 전혀 다른 두 가지 데이터를 함께 담고 있습니다:

- **정적 속성**: `NO`, `CHARGE`, `MODEL`, `LOCATION`, `SIZE`, `DIVISION` — 잘 변하지 않는 기기 메타데이터
- **동적 인증 상태**: `AUTH_KEY`, `AUTH_ISSUE_DATE` — 1분짜리 일회성 인증 토큰

처음에는 인증 상태를 별도 `rental_box_auth` 테이블로 분리하자는 의견이 있었습니다.  
하지만 RBS가 인증 요청을 할 때마다 JOIN이 필요해지고, 장치 수가 늘어나면 조회 성능이 저하될 수 있어 **단일 테이블에 `UPDATE`로 처리**하는 방향을 선택했습니다. `updateAuth` 쿼리가 `AUTH_KEY`, `AUTH_ISSUE_DATE`만 수정하도록 분리된 것도 이 고민의 흔적입니다.

두 번째로 고민이 많았던 테이블은 **`rental`** 입니다. 결제 취소를 `cancellationDate` 컬럼의 null 여부로 표현하는 방식은 단순하지만, "취소된 대여" 조회 시 `cancellationDate IS NULL` 조건을 매번 명시해야 한다는 점에서 상태 컬럼(`status`)으로 분리할지 논의가 있었습니다.

### Q4. 인증 1분 유효 조건을 API로 구현했다고 했는데, 동시 요청이 오면 어떻게 처리됩니까?

**A.**  
솔직히 말씀드리면 **현재 구현에는 동시성 처리가 없습니다.** 이것은 프로젝트 당시 인지한 한계점입니다.

실제 코드(`AuthenticationServiceImpl.compareCardUID`)를 보면:

```java
RentalBox row = rentalBoxMapper.select(rentalBox);  // ① 읽기
if (row != null && row.getAuthKey() != null) {
    LocalDateTime authIssueDate = row.getAuthIssueDate().plusMinutes(1);
    if (LocalDateTime.now().isAfter(authIssueDate)) {
        rentalBoxMapper.updateAuth(row);               // ② 만료 처리 쓰기
    } else {
        isMatched = true;                              // ③ 인증 성공
    }
}
```

읽기(①)와 쓰기(②③) 사이에 gap이 있어, 두 RBS 장치가 동시에 같은 대여함 번호로 요청하면 **두 요청 모두 `true`를 반환할 수 있습니다.**

실제 상용화한다면 다음 중 하나로 해결해야 합니다:

1. **MySQL의 `SELECT FOR UPDATE`** + `@Transactional`로 행 단위 잠금
2. **Redis 기반 분산 락** (Redisson 등)
3. DB에서 `UPDATE rental_box SET AUTH_KEY = NULL WHERE NO = ? AND AUTH_KEY = ?`처럼 **조건부 UPDATE 후 affected rows 확인** — CAS(Compare-And-Swap) 패턴

### Q5. 상태 일관성을 유지했다고 했는데, 어떤 상황에서 깨질 수 있나요?

**A.**  
크게 두 가지 시나리오가 있습니다.

**① 결제 취소 시 외부 API ↔ DB 불일치**  
`PaymentServiceImpl.cancelPayment()`는 아임포트 API 호출 성공 여부와 무관하게 `rentalMapper.update(rental)` (취소일 기록)을 시도합니다. 아임포트 API 호출이 네트워크 오류로 실패해도 예외가 `catch(Exception e) { e.printStackTrace(); }`로 삼켜지기 때문에:

- 외부 결제는 취소 안 됨 → DB에는 취소일이 기록됨 (사용자는 대여함 못 씀, 환불도 안 됨)
- 또는 역으로 외부 결제는 취소됨 → DB 업데이트 실패 (사용자는 돈을 돌려받았지만 DB상 대여 유효)

**② 이용 내역 등록 시 회원 ID 매칭 실패**  
`UsageHistoryServiceImpl.registerUsageHistory()`는 `RENTAL_BOX_NO`로 현재 진행 중인 대여를 조회해 `MEMBER_ID`를 찾습니다. 그런데 이 조회 로직이 날짜 비교 조건(`isBefore`, `isEqual`)을 복잡하게 작성해서, 동시에 여러 대여 레코드가 조건을 만족하면 **마지막으로 매칭된 회원 ID가 덮어쓰여** 잘못된 사람의 이름으로 이용 내역이 등록될 수 있습니다.

### Q6. 인증 만료와 동시에 카드가 찍히면 어떻게 됩니까?

**A.**  
코드상 경계 조건 처리는 다음과 같습니다:

```java
LocalDateTime authIssueDate = row.getAuthIssueDate().plusMinutes(1);
if (LocalDateTime.now().isAfter(authIssueDate)) {
    // 만료 처리
} else {
    isMatched = true;
}
```

`isAfter()`는 **strictly after** 비교입니다. 즉, `LocalDateTime.now()`가 정확히 `발급시간 + 1분`과 **같을 때**는 만료로 처리되지 않아 인증이 통과됩니다. 나노초 수준의 경계 타이밍에서 예상과 반대의 결과가 나올 수 있습니다.

더 현실적인 시나리오: 사용자가 59초에 카드를 찍으면 NFC 수신 → HTTP 요청 → 서버 처리 중 60초를 넘어갈 수 있습니다. 물리적으로는 유효 시간 내에 찍었지만, 서버 처리 시점 기준으로 만료 판정이 날 수 있습니다.

이는 "인증키 발급 후 1분"을 **요청 수신 시각** 기준이 아닌 **서버 처리 시각** 기준으로 판단하기 때문에 발생하는 UX 이슈입니다.

### Q7. 보안적으로 가장 취약했던 부분은 어디였다고 생각하나요?

**A.**  
세 가지를 꼽겠습니다.

**① 비밀번호 평문 저장**  
`MemberMapper.xml`의 `INSERT INTO member ... PASSWORD = #{password}` 와 `WHERE PASSWORD = BINARY #{password}` 에서 알 수 있듯, 비밀번호를 해싱 없이 그대로 DB에 저장합니다. DB가 유출되면 모든 회원의 비밀번호가 즉시 노출됩니다.

**② 결제 API 시크릿 키 하드코딩**  
`PaymentServiceImpl.java` 에 아임포트 `imp_key`와 `imp_secret`가 소스코드에 직접 포함되어 있습니다. 이 키들이 GitHub에 공개되면 타인이 동일 식별코드로 결제 API를 호출할 수 있습니다.

**③ 인증 API 엔드포인트 무보호**  
`/authentication/grantauthinfo`, `/authentication/comparecarduid` 는 세션 체크 인터셉터 경로에 포함되어 있지 않습니다. 즉, **인터넷에서 누구든 파라미터만 알면 인증키를 부여하거나 인증을 통과시킬 수 있습니다.** ADS/RBS 전용 토큰이나 IP 화이트리스트가 없습니다.

### Q8. 만약 이걸 실제 상용 서비스로 만든다면 가장 먼저 고칠 부분은?

**A.**  
우선순위 순으로:

1. **비밀번호 해싱** (`BCryptPasswordEncoder` 적용) — 보안의 기본이고, 기존 코드 변경 범위가 가장 작습니다.
2. **결제 API 키 외부화** — `application.properties` + 환경변수 또는 Vault로 시크릿 분리. 소스코드에 남기면 안 됩니다.
3. **인증 API 접근 제어** — ADS/RBS 전용 사전 공유 토큰 (`X-Device-Token` 헤더 등) 또는 내부망 IP 화이트리스트 적용.
4. **결제 취소 트랜잭션 보장** — 아임포트 API 성공 확인 후 DB 업데이트, 실패 시 예외를 컨트롤러로 전파하여 사용자에게 안내.
5. **인증 동시성 처리** — `SELECT FOR UPDATE` + `@Transactional` 또는 DB 수준 CAS UPDATE로 이중 개방 방지.

### Q9. 요구사항 문서를 왜 개발자가 작성했다고 생각하나요?

**A.**  
두 가지 이유에서 개발자가 요구사항을 직접 작성한 것이 유효했다고 생각합니다.

첫째, **이 프로젝트는 3개 독립 서버(SRUS, ADS, RBS)가 API로 통신하는 구조**입니다. API 계약(어떤 파라미터를 어떤 형식으로 주고받는가)은 구현 가능성을 알아야 정확하게 정의할 수 있습니다. 비개발직군이 작성한 요구사항은 "카드를 찍으면 문이 열린다"에서 끝나지만, 개발자가 작성하면 "RBS가 `GET /authentication/comparecarduid?no={}&authKey={}`를 호출하고 `{"result": true}`를 수신하면 모터를 구동한다"까지 정의됩니다.

둘째, **요구사항 작성 자체가 설계 검증 과정**입니다. 요구사항을 문장으로 만들다 보면 "그렇다면 이 케이스는?" 같은 예외 상황이 자연스럽게 발견됩니다. Q4·Q5·Q6의 동시성·일관성 이슈도 이 과정에서 더 일찍 발견할 수 있었을 것입니다.

### Q10. 문서화가 실제로 일정 단축에 어떻게 기여했나요?

**A.**  
가장 직접적인 기여는 **병렬 개발 가능성** 이었습니다.

SRUS, ADS, RBS 세 팀이 각자 독립적으로 개발하려면 사전에 API 명세(`인터페이스 정의서`)가 확정되어야 합니다. 문서가 없었다면 한 팀이 끝날 때까지 다른 팀이 대기하거나, 통합 단계에서 대규모 수정이 필요했을 것입니다.

두 번째 기여는 **온보딩 비용 절감**입니다. `요구사항 정의서 → 분석서 → 엔티티 정의서 → 테이블 정의서 → 화면 정의서 → 프로그램 목록` 순으로 문서 체계가 갖춰져 있어서, 팀원이 담당하지 않은 기능도 문서를 보고 빠르게 파악할 수 있었습니다.

실제로 README에도 "분석 및 설계를 팀원들과 같이 진행하고, 구현에 들어가니 기존보다 협업이 잘되고, 구현이 쉽게된다는 것을 알게되었습니다"라고 기록되어 있습니다.

### Q11. API 명세서는 어떤 형식으로 작성했나요?

**A.**  
`인터페이스 정의서.docx` (7번 문서) 형식으로 Word 문서에 작성했습니다.

각 엔드포인트는 다음 항목으로 구성했습니다:

- **엔드포인트**: `GET /authentication/grantauthinfo`
- **호출 시스템**: ADS → SRUS
- **요청 파라미터**: `id` (회원 ID), `no` (대여함 번호)
- **응답 형식**: `{"result": true|false}`
- **처리 설명**: 회원의 카드 UID를 대여함의 AUTH_KEY에 기록하고, 발급 시각을 AUTH_ISSUE_DATE에 저장

Swagger나 OpenAPI 같은 도구는 사용하지 않았는데, 해당 도구 지식이 부족했던 점과 Word 문서가 팀원들에게 더 친숙했던 환경이 이유였습니다. 지금이라면 Swagger나 Notion (메서드·경로·파라미터·응답 예시를 컬럼으로 구성한 Database 페이지)으로 작성하겠습니다.

### Q12. 문서 기반 개발이 왜 유지보수 리스크를 줄인다고 생각하나요?

**A.**  
코드는 **"무엇을 했는가(What)"** 를 보여주지만, 문서는 **"왜 이렇게 결정했는가(Why)"** 를 담습니다.

예를 들어, `rental_box` 테이블에 `AUTH_KEY`와 `AUTH_ISSUE_DATE`가 있는 이유는 코드만 봐서는 알 수 없습니다. 엔티티 정의서를 보면 "NFC 인증 시 일시적으로 카드 UID를 해당 대여함에 복사해 1분간 유효한 인증 토큰으로 사용한다"는 설계 의도가 적혀 있습니다. 이 의도를 모르는 개발자가 성능 최적화를 위해 이 두 컬럼을 캐시로 빼거나 삭제하면 전체 인증 플로우가 무너집니다.

또한 테이블 정의서(`8,9,10,11. 테이블 정의서.docx`)처럼 컬럼 별 의미·제약 조건이 문서화되어 있으면, DB 스키마 변경 시 영향 범위를 빠르게 파악할 수 있습니다.

### Q13. 실제 코드와 문서가 달라진 적은 없었나요?

**A.**  
있었습니다. 대표적인 예가 **결제 취소 가능 기간**입니다.

초기 요구사항에서는 취소 정책이 명확하지 않았는데, 구현 단계에서 아임포트 API 연동을 해보니 결제 취소는 대여 시작일 이전까지만 허용하는 것이 합리적이라고 판단해 정책을 확정했습니다. 이 결정은 README의 "결제 취소가 가능한 기간을 결정해야 했었는데 무인 대여함 대여 시작일 전까지 가능한 것으로 결정하였습니다"에 기록되어 있습니다.

이처럼 구현 중 발견한 변경 사항은 가능한 한 관련 문서(요구사항 정의서, 화면 정의서)에 반영했지만, 빠른 속도로 개발이 진행되면서 일부 문서가 코드를 따라가지 못한 경우도 있었습니다. 이 경험을 통해 문서를 한 번에 완벽하게 쓰는 것보다 **변경 시 즉시 업데이트하는 습관**이 더 중요하다는 것을 배웠습니다.

### Q14. 팀원이 문서를 안 지키면 어떻게 했나요?

**A.**  
먼저 **"안 지켜서 실제로 문제가 생긴 상황"을 구체적으로 보여주는 방법**을 사용했습니다.

예를 들어, RBS 팀이 인터페이스 정의서와 다른 파라미터 이름을 사용하면, SRUS 서버의 `AuthenticationController`에서 바인딩이 되지 않아 null이 넘어오고 `NullPointerException`이 발생합니다. 이 오류 로그를 직접 보여주면서 "API 계약이 다르면 두 팀 모두 추가 작업이 생긴다"고 설명했습니다.

단순히 "문서를 지켜야 한다"는 당위보다, **문서를 안 지켰을 때 내 작업이 아닌 팀 전체의 일정이 영향받는다**는 것을 구체적으로 연결지으면 팀원들이 더 잘 따라줬습니다.

장기적으로는 API 명세를 Swagger처럼 코드에서 자동 생성하는 방식이 "문서를 별도로 관리한다"는 부담을 없애는 더 좋은 해결책이라고 생각합니다.
